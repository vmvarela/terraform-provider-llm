# Agent Guidelines

## Project Status

The provider is implemented and verified locally: `internal/provider/` holds
the provider configuration, the `llm_generation` resource, an HTTP client, and
unit plus acceptance tests; `docs/` is generated by `terraform-plugin-docs`.
The provider is not published to the Terraform Registry, has no release, and
live endpoint compatibility is untested. Do not describe it as released or
compatibility-verified against any real backend.

All code, documentation, examples, diagnostics, and commit messages must be in
English. Preserve unrelated user changes. Never read, source, print, or commit
`.envrc` or other local credential files unless explicitly authorized.

## Scope

- Provider: `llm`; repository: `terraform-provider-llm`.
- Planned resource: `llm_generation`, a logical snapshot of generated content.
- Use the OpenAI-compatible Chat Completions HTTP contract, not a vendor SDK.
- First release: text messages, plain text output, and JSON-object output.
- Defer JSON Schema, streaming, tool execution, agents, multimodal inputs, and
  native adapters for incompatible vendor APIs.
- Do not add data sources that generate content during planning or refresh.

## HashiCorp Conventions

- Use the Terraform Plugin Framework for new provider code, with Go modules.
- Follow the official scaffolding repository's structure without retaining
  unrelated example resources or speculative abstractions.
- Put provider configuration and resources in `internal/provider/`. Introduce
  other packages only when they have a concrete responsibility.
- Keep executable examples in `examples/`; generate Registry documentation in
  `docs/` with `terraform-plugin-docs`. Edit schemas, descriptions, examples, or
  templates rather than hand-editing generated documentation.
- Keep resource and attribute names close to the API, prefixed with `llm_` for
  resource types. Distinguish configured `model` from returned model metadata.
- Respect Terraform null, unknown, sensitive, plan, and state semantics. Never
  rewrite a configured value to match an API response.
- Preserve state compatibility once released. Use semantic versioning,
  deprecation notices, and state upgrades when warranted by shipped behavior.
- Document the logical-resource exception: no portable remote lookup, deletion,
  or import. Do not fabricate import support from an unrecoverable response ID.

## Resource Contract

- `Create`: generate during apply, validate the response, then save the snapshot.
- `Update`: regenerate when messages, model, generation parameters, or an explicit
  `generation_key` change. Preserve the previous ID and snapshot on failure;
  return an error rather than pretending the new configuration succeeded.
- `Read`: preserve state without generation or remote lookup.
- `Delete`: remove the snapshot from Terraform state without a remote request.
- New output is unknown during planning whenever regeneration is required. Never
  use `UseStateForUnknown` to retain output that will change during apply.
- Use a stable local resource ID, separate from optional API response IDs.
- Provider configuration changes do not automatically produce resource diffs.
  Document explicit regeneration through `generation_key` for backend changes;
  credential rotation alone must not regenerate content.
- Validate JSON-object output locally before committing a successful snapshot.
  Terraform postconditions can block dependents, but do not roll back generation
  or a snapshot already written to state.

## HTTP and Security

- Prefer `net/http` and `encoding/json`; avoid a vendor SDK or generic plugin layer.
- Support configurable API base URLs and optional bearer authentication, including
  local endpoints without credentials. Do not require model discovery endpoints.
- Honor cancellation and timeouts. Bound response reads, check HTTP status, and
  handle malformed, missing, refused, or truncated output explicitly.
- Never disable TLS verification or forward credentials to an untrusted redirect.
- Do not automatically retry ambiguous POST failures or claim exactly-once
  execution. A failed or interrupted request may still have incurred charges.
- Keep credentials in provider configuration, not resource attributes. Mark
  credential fields sensitive and avoid logging request or response bodies.
- Treat prompts and generated content as potentially sensitive. They are persisted
  in state; `Sensitive` redacts display but does not encrypt or omit values.
- Diagnostics must be actionable without exposing credentials, sensitive URLs,
  prompts, or raw API error bodies that may echo user input.

## Verification

Use Go tests for HTTP parsing and validation, and `terraform-plugin-testing` for
real Terraform lifecycle coverage. Back default tests with `httptest` endpoints
and request counters; do not require paid APIs or local credentials in CI.

Acceptance evidence must cover initial generation, a subsequent empty plan,
zero requests on refresh/destroy, changed-input regeneration, unknown inputs,
failed-update state preservation, JSON validation, and credential redaction.
Check that credentials are absent from resource state, not that prompts and
outputs are absent. Add tests for backend changes and explicit regeneration.

Verify changes with:

```sh
go build ./...
go vet ./...
go test ./...
TF_ACC=1 go test ./internal/provider/ -run TestAcc -count=1
go generate ./...
terraform fmt -check -recursive examples/
```

Documentation generation runs the nested tools module (`go -C tools generate`,
driven by root `go generate ./...`) and must produce no diffs. The default
`terraform` on PATH may be an alpha locally; acceptance evidence on stable
Terraform (1.13/1.14) takes precedence.

Keep Go files formatted with `gofmt`. Validate examples using the development
provider once available. Require explicit opt-in for live endpoint tests and
report untested compatibility rather than inferring it from a configurable URL.

## Release Boundaries

Before publishing, establish the namespace, license, supported Go/Terraform
versions, CI checks, and signed release workflow following HashiCorp's publishing
guide. Do not invent a Registry address, license, release badge, or compatibility
claim. Do not commit, tag, push, or publish without explicit authorization.
